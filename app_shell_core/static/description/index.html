App shell core

Core tools to publish single page apps (SPA) from Odoo, without Odoo’s web client and assets bundles: the app is made of plain ES modules served from the static folder of its modules.

This first version provides the loading of the app’s JS via an import map:

  • every JS file of the app is loaded from a versioned URL (module version or hash of the content), so that a file is downloaded again only when it changes, with no version to put in the code;
  • every module is loaded from a single URL, hence a single instance, no matter how it’s imported (relative or absolute path);
  • any JS module can be replaced by another one server side, everywhere it is imported.

It’s exposed by app.shell.mixin.importmap, to inherit on the model describing your app. It’s the first piece of a generic “app shell”, see the roadmap.

Important

This is an alpha version, the data model and design can change at any time without warning. Only for development or testing purpose, do not use in production. More details on development status

Usage

Expose the import map of an app

Inherit app.shell.mixin.importmap on the model describing your app and return the modules providing the app’s JS:

class MyApp(models.Model):
    _name = "my.app"
    _inherit = ["app.shell.mixin.importmap"]

    def get_app_js_root_modules(self):
        return ("my_app_frontend",)

The import map covers the JS files of the root modules (one or more) and of all the installed modules depending on them, each one mapped to a versioned URL. The method is called on the app record: the root modules can depend on it.

Example, for my_app_frontend:

{
  "imports": {
    "/my_app_frontend/static/src/main.esm.js": "/my_app_frontend/static/src/main.esm.js?v=18.0.1.0.0"
  }
}

The map applies to every import, relative (./foo.esm.js) or absolute (/other_module/static/src/foo.esm.js): every file is loaded from its versioned URL, without any version in the code, and all the modules importing the same file get the same instance of it.

The list of files is computed once per process (files change only on deploy), or on every call in dev mode (--dev) so that new files are picked up without restarting.

Pass the app record to the template of the app’s page (eg: as app) and render the import map in <head>, before any ES module, passing it explicitly:

<t t-call="app_shell_core.importmap">
    <t t-set="importmap" t-value="app.make_app_importmap()" />
</t>
<script type="module">
    import "/my_app_frontend/static/src/main.esm.js";
</script>

You decide which map is rendered: eg: one built or extended by your own code.

Load ES modules with an inline module importing the plain URL (no version): the import map does not apply to the src attribute. Classic scripts and stylesheets get their versioned URL from get_app_static_url:

<link
    t-att-href="app.get_app_static_url('/my_app_frontend/static/src/main.css')"
    rel="stylesheet"
/>

Versioning

js_version_mode decides the version appended to the URLs:

  • Module version (default): the version of the module providing the file. No file is read. Files are downloaded again only when the module version changes. Override get_app_js_module_version for another policy (eg: a project version).
  • File content: a hash of the content of each file, read once per worker process (until the file changes on disk).

Replace a JS module

Override get_app_js_overrides to replace a module everywhere it is imported. The replacement can still import the original URL to extend it (via import map scopes), and must export the same names. When several modules replace the same URL, each one gets the previous one.

Browser support

Import maps are supported by Chrome/Edge 89+, Firefox 108+ and Safari 16.4+. Older browsers ignore the map: modules are loaded from their plain URL, without versioning, and overrides are not applied.

Known issues / Roadmap

This module is the first piece of a generic app shell: the core tools to publish single page apps (SPA) from Odoo, without Odoo’s web client, so that any app can use them, not only the Shopfloor ones.

It lives in its own repository, OCA/web-app-shell, together with the satellite modules below. Shopfloor (OCA/shopfloor-app) is its first user and becomes one of its consumers.

Structure

A small core, plus satellite modules for specific features. Each satellite is a feature someone can install on its own, not one module per file.

  • ``app_shell_core`` (this module): generic and dependency-free.
    • Import map, versioning, overrides, and the app.shell.mixin.importmap.
    • App page and PWA plumbing: page controller, manifest, icons, app info.
    • Runtime registries: config, generic registry, utils, colors.
    • REST client (odoo.esm.js, fetch.js) and the vanilla event hub.
    • Auth handler registry (the auth modules plug into it).
  • ``app_shell_bus``: client for Odoo’s bus (websocket worker, no Odoo web client), the app’s bus channel, and the worker version in app info. Depends on core and bus.
  • ``app_shell_sync``: sync manager, version detection and update flow, upgrade manager, connectivity status. Depends on core and app_shell_bus. Kept apart from the bus, so that an app can receive notifications without the sync behaviour.
  • ``app_shell_i18n``: translation registry, the en/fr/de catalogues, and the language settings page. Depends on core only.
  • ``app_shell_demo``: the demo mode machinery and the mocked backend. Demo data stays in each app: only the framework moves.
  • ``app_shell_ui``: generic UI components and theme: screen, list, manual select, searchbar and filters, date picker, number spinner, priority widget, user information and confirmation, report issue, detail card and mixin. These are Vue 2 components today: the module is named by purpose, and a Vue 3 rewrite is expected to replace them rather than move them.
  • Auth modules (eg: shopfloor_mobile_base_auth_api_key) stay satellites of core, as today.

Suggested order: core, then app_shell_bus (already built), then app_shell_i18n and app_shell_ui (cheapest moves, most reuse), then app_shell_sync (depends on the bus), then app_shell_demo once another app needs it.

Stays in the app module (Shopfloor)

The domain part, which is not a shell concern:

  • scenarios: the scenario state machine (scenario/mixins), form scenarios, and the scan-anything service;
  • profiles and menus: the profile settings page and the menu wiring;
  • router and homepage, which map the app’s menus and scenarios to routes;
  • the Shopfloor app record and its app info.

Open points

  • loginpage: generic, but tied to the auth flow. Move it with auth.
  • settings: the settings page registry is generic, the profile entry is not.
  • App record basics (URL, auth type, languages, running environment), now in shopfloor_base: they belong in core too. A separate and larger move.

Design principles

  • No dependency on base_rest or component in the core: REST services belong to each app.
  • Mixins on the app’s model rather than new tables, so that apps adopt the pieces without data migration.
  • Backward compatibility for apps moving to it: template ids kept as extension points, legacy import map entries for moved JS files.
  • Framework-agnostic runtime services (plain JS), so they can be shared by Vue 2, Vue 3 or plain JS apps.

Short term

  • Test the mixin in the core itself, with a test app model (today tested through shopfloor.app in shopfloor_mobile_base).
  • Reusable UI test commands and tasks, the docker compose setup and the CI workflow, to test apps in a real browser.
  • Support Odoo 16, to backport and forward port the same files.
